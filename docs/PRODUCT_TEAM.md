# 제품 개선 조직과 실사용 검수

작성: 2026-09-21. 사용자의 지속 개선 요청에 따라 역할별 검토 → 구현 → 다른 역할의 재검수 → 실제 실행을 반복한다. 아래 역할은 에이전트가 맡는 검토 관점이며 실제 고객 인터뷰나 법률 전문가의 승인을 대신하지 않는다.

## 사용자 확정 기준 · 2026-09-21

- 기본 안내는 **단계 안내 + 전체 지도**다. 한 번에 한 가지 행동을 제시하고 전체에서 현재 위치와 남은 확인을 찾을 수 있게 한다.
- **모바일 현장 사용을 우선**한다. 작은 화면에서 입력·저장·재개·자료 확인을 끝낼 수 있어야 한다. PC 화면은 같은 기록을 정리하는 보조 환경이다.
- **시설관리 사업장부터 검증한 뒤 확대**한다. 전 산업으로의 확대 목표를 첫 고객의 검증 완료로 대신하지 않는다.
- Supabase 개발 환경은 **아직 없다**. 현재 범위는 연결 준비와 로컬 검증이며 실제 Auth·Storage·검사·복구 검증은 연결 후 별도 통과해야 한다.

## 13개 페르소나와 판단 책임 · 2026-09-23

실제 사람의 발언이나 조사 결과가 아니라 **서로 다른 조건을 가진 검토 관점**이다. 나이만으로 능력을 단정하지 않고 글씨·조작·기억 부담 등의 조건을 분리한다. 한 에이전트가 여러 관점을 맡아도 독립된 고객 수로 집계하지 않는다.

매 회차는 [제품 검토 목록](PRODUCT_REVIEW_BACKLOG.md)의 미해결 문제에서 시작한다. 범위가 다른 업종·규모의 반례도 검토하되 실제 지원 검증은 시설관리부터 진행한다. 외부 법령 검토자는 실제 자격·책임과 승인 기록을 갖춰야 하며 위 P08 가상 역할이 대신 승인할 수 없다.

## 반복 절차

1. 현재 코드와 이전 검증 결과를 읽고 구체적 실패 시나리오를 제시한다. 과거 문제를 현재 문제로 재사용하지 않는다.
2. 각 역할은 다른 역할의 제안에 반론을 제시한다. 논의가 끝나면 제품 책임자가 우선순위와 파일 소유권을 확정한다.
3. UI만이 아니라 저장·재열람·보완·권한을 포함해 구현한다. 기존 데이터와 미완료 항목을 보존한다.
4. 구현하지 않은 역할이 변경 코드를 검수한다. 발견한 결함을 수정한 다음 관련 자동 검증을 실행한다.
5. `PROGRESS.md`와 제품 검토 목록에 재현 단계, 증거, 반론, 결정, 변경 파일, 실제 검사 결과, 미실행 항목을 남긴다. 다음 회차는 남은 가장 큰 사용자 장애에서 시작한다.
6. 상태는 관찰 → 재현 → 수정 → 독립 검수 → 로컬 검증으로 옮긴다. 실제 연결·고객·전문가 검증 대기는 별도로 유지한다. 구현 담당자의 자기 확인만으로 독립 검수를 통과시키지 않는다.
7. P0(노출·원본 손실·거짓 법적 판정)와 P1(핵심 과제 중단·입력 손실·근거 회수 불가)은 출시 범위에서 해결하거나 해당 범위의 제공을 명시적으로 보류한다. 취향·꾸밈 의견은 사용 실패보다 앞세우지 않는다.

## 통과 조건

- **로컬 제품 기능:** 처음 시작 → 실제 사실 입력 → 저장 → 재방문 → 보완 → 지난 기록 찾기가 이어진다. 오류·재시도·중복 요청·다른 고객 접근도 검사한다.
- **실제 연결:** 실제 Auth·MFA·DB·비공개 Storage·파일 검사·다운로드 권한 철회가 시험 환경에서 작동한다. 데모 또는 PGlite 통과를 이 조건의 통과로 쓰지 않는다.
- **운영:** DB와 원본 파일을 함께 복구하고, 검토 배정·보완 대기·장애 대응을 담당자가 수행한다. 지원시간과 검토 범위를 실제 처리능력에 맞춘다.
- **법령:** 고객에게 제공할 판단 범위에 대해 출처와 시행일을 확인하고 승인된 규칙을 배포한다. 미승인·미응답을 해당 없음으로 만들지 않는다.
- **고객 검증:** 실제 초보 고객이 도움 없이 다음 행동과 저장/수행/검토의 차이를 설명하고 핵심 과제를 완료한다. 에이전트 페르소나 검토와 별도다.

위 조건을 테스트 개수나 임의의 상품화 점수로 합산하지 않는다. 실제 연결·운영·법령·고객 검증 전에는 정식 실사용 준비 완료라고 보고하지 않는다.

## 첫 개선 회차 결정

외형을 더 꾸미는 접근, 실제 연결만 먼저 준비하는 접근, 반복 업무와 자료 회수를 먼저 완성하는 접근을 비교했다. 현재 글꼴·그림은 이미 개선됐고 외부 연결 설정은 없으므로, 세 번째를 먼저 구현하면서 연결 차단 요인을 별도로 유지한다.

- 평가 회차와 수정 버전을 분리한다. 새 회차는 빈 기록으로 시작하고 이전 회차를 출처로 연결한다. 참석·수행·검토 결과를 자동 복사하지 않는다.
- 여러 위험요인 중 마지막에 보던 항목을 안정 ID로 재개한다. 삭제된 항목을 다른 항목으로 오인시키지 않는다.
- 100건을 넘는 자료와 검토 요청도 권한 범위에서 검색·페이지 이동으로 찾는다. 검토는 실제 요청 시각을 기준으로 정렬한다.
- 이후 파일 업로드 실패·검사 대기 복구를 다시 검토한다. 연결 설정·실제 법령 승인·사용자 실험은 완료 증거가 생길 때까지 미완료로 유지한다.

## 실제 고객 검수 과제 — 아직 미실행

사용자가 확정한 시설관리·유지보수 현장의 초보 담당자와 모바일 현장 사용을 우선한다. 실제 인원을 초대하거나 고객 원본을 데모에 입력하지 않는다. 참여가 준비되면 접근 통제가 검증된 시험 환경에서 실제 휴대전화로 아래를 관찰한다. 가상 키보드·한 손 조작·현장 네트워크에서의 시험은 데스크톱 브라우저 화면 폭 검사와 구분한다.

1. 처음 접속해 지금 할 일과 확인하지 못한 사실을 말하고 첫 기록을 저장한다.
2. 위험요인 세 개 중 두 번째 조치를 작성하다 종료한 후 같은 위치에서 이어 쓴다.
3. 첫 회차를 보완한 v2와 새로운 두 번째 평가의 v1을 구별하고, 지난 미해결 위험을 찾는다.
4. 파일 저장 실패 안내를 읽고 원본을 보존하며 재시도한다. 검사 완료와 내용 확인의 차이를 설명한다.
5. 다른 현장의 지난 기록과 검토 의견을 검색하고 회차·버전을 확인한 뒤 보관 사본을 받는다.

각 과제에 성공 여부, 도움 요청, 잘못 이해한 상태, 잃어버린 입력 여부를 기록한다. 심각한 오해나 데이터 손실이 발생하면 문구만 평가하지 말고 원인을 수정한 뒤 같은 과제를 다시 수행한다. 에이전트 검토·자동 테스트 결과를 이 표의 실제 고객 결과로 대신 기록하지 않는다.
