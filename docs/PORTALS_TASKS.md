# 회원 업무 기록과 중앙관제 연결

## 이용 흐름

- 공개 첫 화면에는 회원 로그인·가상 체험·긴급 연락만 표시한다. 중앙관제 주소는 `/ops/login`이며 공개 탐색에 넣지 않는다.
- `/app`은 회원 전용 가상 체험, `/workspace`는 실제 인증·저장을 사용하는 회원 공간이다. 내부에서 운영자 역할로 전환하지 않는다.
- 회원 홈에서 등록정보 → 업종·실제 작업 → 인원·고용관계 → 입력 확인을 먼저 진행한다. 임시 저장은 재접속해 이어 쓸 수 있고, 확인 저장 후 관련 업무와 전체 후보 열람을 연다.
- 기존 78개 조사 후보 중 사업장 분류·인원 확인 2개를 입력 단계로 분리한다. 업무 목록은 나머지 76개 중 관련 후보를 표시하고, 사진·계획은 보조 도구로 제공한다. 등록정보 자체 서식의 기존 기록은 보존한다. 이 수를 전체 법정 의무 수로 표시하지 않는다.
- 후보 열람은 읽기 동작이다. ‘관리 시작’으로 현장에 항목을 추가한다. 담당·목표일만 임시 저장할 수 있고, 확인 내용이 생기면 문서 버전과 증빙·검토·수행 기록을 연결한다.
- 자료 준비 목표일은 사용자가 정한 일정이다. 한국 날짜 기준 경과/7일 이내를 표시하며 검토 대기·자료 검토 완료는 준비 기한 강조에서 제외한다. 실제 수행·기관 접수 완료로 바뀌지는 않는다.
- 자료가 없는 업무는 같은 현장의 기존 자료를 연결할 수도 있다. 원본·버전·검토 이력을 보존하고 이미 연결된 자료는 바꾸지 않는다.

## 실제 환경 적용 순서

1. `P2_SETUP.md`의 비공개 시험용 Supabase 설정을 준비한다. 키를 채팅·문서·브라우저에 넣지 않는다.
2. `supabase/migrations`의 SQL을 파일명 순서대로 적용한다. 기존 0001~0003 적용 환경은 0004(업무·운영자), 0005(후보 메타데이터), 0006(쓰기 권한 조회), 0007(사업장 선입력·확인)을 추가한다. 0005의 메타데이터는 승인된 법령 규칙이 아니다. 0007은 기존 프로필을 자동 확인하지 않으며 구 4인자 저장 RPC를 제거하므로 앱과 함께 적용한다.
3. 실제 운영자는 회원 계정과 별도 Auth 계정을 만든다. 운영 DB 관리자가 아래 등록을 수행한 후 기존 고객·현장 배정 절차를 적용한다. 실제 계정 생성·메일 발송은 실행 권한을 확인한 범위에서 수행한다.

```sql
-- 아래 UUID는 실제로 생성한 별도 운영 계정의 auth.users.id로 치환한다.
insert into app_private.safety_operators(user_id, role)
values ('운영 계정 UUID', 'reviewer');
```

- `reviewer`: 추가 인증과 유효한 현장 배정이 있어야 자료를 읽고 검토한다. 민감자료 권한은 별도다.
- `rules_admin`: 법령 준비 접근 권한이다. 현장 자료 검토 권한을 자동 부여하지 않는다.
- 같은 계정에 회원 소속과 운영자 등록을 겸할 수 없도록 DB에서 검사한다. 기존 검토자 배정만으로 운영자 등록을 자동 생성하지 않는다.
- 철회는 `active=false`로 처리한다. 운영자 등록·변경은 비공개 이력 테이블에 기록한다. 일반 앱 계정은 이 테이블을 읽거나 수정할 수 없다.
- `/ops/login`에서 로그인 후 인증 앱을 등록·확인한다. 중앙관제는 운영자 등록·추가 인증·배정·민감자료 권한을 함께 검사한다.

## 데이터와 권한

- 업무 메타데이터는 `safety_tasks`, 사업장 입력 사실·탐색 조건·revision·확인 시각은 `safety_workplace_profiles`에 저장한다. 사용자 입력 확인을 법령 적용 승인과 구분하며, 이전/이후 정보를 감사 이력에 보존한다. 인원 집계는 법령별 산정 결과가 아니다.
- 확인 내용은 기존 문서 버전으로 저장한다. 직접 원문 SELECT를 허용하지 않고 기존 감사 RPC로 읽는다.
- 업무 시작·수정·문서 연결·탐색 조건 변경은 서버 검증과 DB 권한 검사 후 감사 이력을 남긴다. 현장과 문서의 복합 외래키, 업무·문서 revision으로 고객 혼합과 오래된 변경을 거부한다.
- 민감자료를 포함할 업무는 시작할 때 별도 권한 표시를 선택한다. 해당 읽기·쓰기 권한이 없는 계정은 저장·열람할 수 없다.
- 실제 파일은 기존 비공개 격리 저장과 검사 상태를 유지한다. 검사 공급자가 연결되지 않았으면 다운로드·내용 확인을 허용하지 않는다.

## 검증 실행

```text
npm.cmd test
npm.cmd run test:db
npm.cmd run lint
npm.cmd run build
npm.cmd run test:e2e
```

브라우저 명령은 기본 3015번 포트에 전용 서버를 띄우고 종료한다. 포트가 사용 중이면 그 서버를 종료하지 않고 실패한다. 필요하면 `PLAYWRIGHT_PORT`를 다른 빈 포트로 지정한다.

회원·검토자 시험은 서로 다른 브라우저 세션에서 같은 가상 업무를 처리한다. 테스트 실행기가 그 서버에만 임의 인증 토큰과 시험 설정을 전달한다. `/api/testing/session`은 시험 설정과 토큰이 모두 없으면 404이며 live에서는 항상 차단한다. 일반 개발·확인용 서버와 `.env.example`에는 시험 설정을 넣지 않는다.

실제 Supabase Auth/MFA/PostgREST/Storage, 검사 공급자와 DB+원본 파일 복구는 실제 연결 뒤 별도 검증해야 한다. 로컬 PostgreSQL·브라우저 시험을 외부 서비스 성공으로 보고하지 않는다.
