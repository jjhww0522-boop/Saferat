# 사업장 정보 선입력과 관련 업무 목록

## 사용자 흐름

등록정보 → 업종·실제 작업 → 인원·고용관계 → 입력 확인 → 관련 업무 목록.

- 입력은 업무·서류가 아닌 사업장 기본정보로 보관한다. 임시 저장 후 재접속할 수 있고, 확인 저장 후 목록을 연다.
- 사업장명·실제 장소·실제 작업을 최소 입력으로 요구한다. 등록정보·업종·인원 등 미확인 사실은 추가 확인 대상으로 남긴다. 0명과 미응답을 구분한다.
- 직접고용 중 기간제·단시간은 부분집합으로 검사한다. 파견·다른 업체 인원을 모든 법령의 인원으로 합산하지 않는다.
- 업종·작업·도급 관계를 기존 검토 후보의 관련성 탐색에 사용한다. 인원은 검토 순서에만 사용하고 항목을 제외하지 않는다. 조문·예외·개별 기준이 승인되기 전에는 법적 의무를 확정하지 않는다.
- 등록정보 및 분류·인원 산정 후보는 업무 목록에서 분리한다. 사진·계획 기록은 보조 도구로 제공한다. 기존 기록은 보존하고 다시 열 수 있다.

## 구현과 검증

1. 공통 입력 스키마·4단계 화면·저장 액션: 초안/확인 구분, 실패 입력 유지, revision 충돌 검사.
2. DB 마이그레이션·RLS/RPC: 이전 정보 감사 이력, 확인 전 신규 업무 생성 차단, 레거시 RPC 우회 차단.
3. 업무 목록 연결: 현장별 정보, 추가 질문, 정보 변경 시 관련 후보 갱신, 기존 작성 업무 유지.
4. 단위·DB·브라우저 검증: 0/미응답, 직접 URL·다른 현장, 저장 재시도, 조문 안내, 모바일·접근성.

사용자 지시와 이미 승인된 구현 범위에 따라 진행하며 별도 계획 재승인을 요청하지 않는다. 실제 법령 승인·Supabase 연결·파일 검사·운영 배포를 완료로 간주하지 않는다.

## 병렬 작업

사용자가 요청한 Orca orchestration으로 Astra medium 작업자 3개를 DB·화면 연결·테스트에 배정한다. 조정자는 도메인·입력 폼·서버 액션·통합 검증과 문서를 맡는다. 같은 파일의 동시 편집을 피한다.
