# P2 인증·저장 기반

## 범위와 결정

사용자의 다음 작업 진행 지시에 따라 P2를 진행한다. 기존 P0·P1 및 검토 목록의 미커밋 변경을 보존한다. 기존 기획대로 Supabase Auth/PostgreSQL/Storage를 사용하며 기존 데모 저장소에 실제 자료를 섞지 않는다.

- 대안: 데모 상태 전체를 JSON으로 저장하면 구현은 짧지만 현장별 외래키·행 권한·원본 버전을 DB에서 검증하기 어렵다. 정규화 테이블과 제한된 트랜잭션 RPC를 선택한다.
- `/workspace`는 실제 인증을 사용하는 자료·검토 공간이다. `/app`·`/ops`는 기존 데모 경로로 유지하고 live 모드에서 접근을 차단한다.
- 실제 계정·키가 없으므로 외부 API 성공을 가정하지 않는다. Supabase 연결부와 설정 안내를 구현하고, PostgreSQL WASM 엔진 PGlite에서 실제 SQL·RLS·트랜잭션을 실행한다. 이는 Supabase Auth/Storage 서비스 통합 검증과 구분한다.
- 로그인 사용자라도 조직의 활성 소속과 현장 권한을 모두 갖춰야 한다. 검토자는 기간 내 배정·업무 범위와 AAL2 추가 인증이 필요하다. 민감자료 권한은 별도다.
- 새 버전·검토·수행·열람 이력을 보존한다. 일반 클라이언트에는 직접 수정·삭제 권한을 주지 않고 검증된 RPC만 허용한다. 법적 적용·승인·기관 접수는 자동 생성하지 않는다.
- 원본 파일은 비공개 격리에 업로드한다. MIME/크기/시그니처 사전 검사와 전문 파일 검사 결과를 구분한다. 검사 공급자가 없으면 다운로드·미리보기는 차단한다.
- 초대는 대상 이메일과 현장·역할에 묶인 만료 토큰이다. 링크 생성과 실제 외부 발송을 구분하며 자동 발송하지 않는다.

## 검증 계획

1. SQL 마이그레이션 실행 → 고객·현장·민감자료 격리, 역할 변조·혼합 외래키·직접 쓰기 차단.
2. 실제 SQL로 자료 v1 → 확인·검토 요청 → 보완 → v2 → 재검토, 동시 수정·중복 요청·과거 이력 확인.
3. DB 종료·재개 및 백업 데이터 복원 → 자료·권한·철회 상태 유지.
4. 서버 연결부 계약·파일 검사·미설정 상태 테스트, 타입·린트·빌드 및 기존 브라우저 시나리오 회귀 확인.

## 외부 완료 조건

Supabase 프로젝트 설정, 실제 Auth/MFA·Storage/API 통합 검증, 파일 검사 공급자, DB와 실제 파일의 복구 시험, 현장 사용자 검증은 별도 확인한다. 이 조건이 남아 있으면 P2 실사용 완료로 보고하지 않는다.
